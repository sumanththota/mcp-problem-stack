Rate-Limit / Fallback Router

A gateway that enforces a token-aware sliding-window rate limit (50,000 tokens/minute) per tenant, using a reserve-then-reconcile SQLite ledger: each request reserves its worst case (prompt + max_tokens) at admission, then that reservation is corrected down to actual usage once the response completes — or force-released by a background TTL sweep if it never does. Separately, the gateway fails over from a primary to a secondary model provider on a 429 or a 3000ms timeout, and every gateway-constructed failure comes back in one sanitized JSON shape. Built as nine tracer-bullet tickets (T1–T9); T9 is the hardening pass that proves the design under real concurrent and crash conditions rather than assuming it.

What this build actually had to decide

Four hard calls, grounded in the code

limiter.py

Reserve-then-reconcile, one atomic transaction

Admission charges the worst case (prompt_tokens + max_tokens) up front, inside a BEGIN IMMEDIATE transaction so the read-then-write can't race across connections. settle() later corrects that same row down to actual usage — but only if it's still pending; a settle arriving after the TTL sweep already expired the row is dropped, not silently revived.

def admit(conn, tenant_id, prompt_tokens, max_tokens, *, request_id=None): reserve = prompt_tokens + max_tokens conn.execute("BEGIN IMMEDIATE") current = ... SUM(tokens) WHERE ts > cutoff ... if current + reserve > BUDGET_TOKENS: conn.rollback(); return False, None ... INSERT ... status='pending' ...

T9's hardening test proves this holds under real threads, not just cooperative asyncio scheduling: 40 concurrent admits for one tenant, each on its own connection to the same on-disk file, land exactly 25 — never more, never fewer.

router.py

The "late primary response" race needed no special handling

The design session flagged a race: what if the primary replies right after the gateway has already failed over to the secondary? The answer, verified rather than assumed: asyncio.wait_for() cancels the underlying primary call on timeout, so a timed-out call structurally can never produce a result call_with_fallback() would see.

async def call_with_fallback(client, body): try: response = await call_primary(client, body) if response.status_code != 429: return response, "primary" except PrimaryTimeout: pass # fall through to secondary response = await call_secondary(client, body) return response, "secondary"

No dedup flag, no cancellation token to thread through — the race the task worried about doesn't exist in this event loop, and a unit test against a mocked transport proves it rather than asserting it by inspection.

errors.py + app.py

One shape, even for the failure nobody expected

Every gateway-constructed failure — over budget, both providers down, or anything unhandled — returns the same {"error": {"code", "message", "request_id"}}. The first two are explicit branches in the endpoint; the third is a global FastAPI exception handler, so a bug three layers down still can't leak a stack trace to a tenant.

@app.exception_handler(Exception) async def unhandled_exception_handler(request, exc): request_id = request.state.request_id logger.exception("unhandled error for request_id=%s", request_id) return errors.error_response(errors.INTERNAL_ERROR, ..., request_id)

The request_id is minted once, at the very top of the handler — before admission even runs — so a rejected request's error response still carries one to quote back for support.

ttl_sweep.py

The TTL is derived, not invented

TTL_SECONDS = PRIMARY_TIMEOUT_S + SECONDARY_TIMEOUT_S + MARGIN_S, imported directly from router.py so the two constants can never silently drift apart. A heartbeat-refreshed TTL was considered and rejected: it only earns its complexity if something can legitimately run unbounded, and nothing here does — every provider call already has a hard timeout.

T9's crash-recovery test runs the actual run_sweep_loop() background task — not a direct sweep() call — abandons a reservation, and confirms the real loop frees it autonomously once TTL elapses. test_ttl_sweep.py already proved sweep() itself is correct; this proves it's really wired up.

Both admit() and sweep() operate on the exact same ledger table through the exact same connection (app.state.db) — there's no separate crash-recovery store to keep in sync.
